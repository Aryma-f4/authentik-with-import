# SSO architecture and configuration design

## Purpose

Add an Indonesian-language Topics documentation page that explains how authentik supports single sign-on (SSO) with OAuth2/OpenID Connect (OIDC) and SAML. The page serves administrators who need both a conceptual model and a short configuration workflow.

## Scope

- Add one Markdown page under `website/docs/add-secure-apps/providers/`.
- Write explanatory text, headings, procedures, and diagram labels in Indonesian. Preserve standard protocol names, authentik UI labels, URLs, and code identifiers in their original form.
- Describe authentik as the identity provider for downstream OAuth2/OIDC relying parties and SAML service providers.
- Include Mermaid diagrams for:
  - The relevant persistent-model relationships: users, groups, applications, providers, authenticated sessions, OAuth2 grants/tokens, and SAML sessions.
  - OAuth2/OIDC authorization-code SSO.
  - SAML SP-initiated SSO.
- Add concise, UI-aligned procedures for creating an OAuth2/OIDC provider and a SAML provider, with links to the detailed protocol guides.
- Add protocol-specific verification and security guidance.
- Register the page in the Topics docs sidebar through the existing autogenerated Providers hierarchy.

## Content design

The page opens with a short explanation of the roles and decision criteria. A database diagram clarifies that an application has one provider, while provider-specific sessions and grants connect to authenticated user sessions. Two sequence diagrams then show the browser and back-channel exchanges for OAuth2/OIDC and SAML.

The configuration section follows the Admin interface workflow: create the provider, attach it to an application, transfer the provider metadata to the relying party or service provider, and test with an assigned user. The document does not duplicate every field from the detailed setup pages.

## Boundaries

- This is a general reference, not a guide for a particular third-party application.
- It does not change the authentik data model, provider behavior, or generated API schema.
- It does not cover inbound federation, SCIM, LDAP, or protocol-specific extensions beyond links to existing documentation.
